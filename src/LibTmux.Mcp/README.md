# LibTmux.Mcp

A server that gives an assistant hands on tmux over the
[Model Context Protocol](https://modelcontextprotocol.io/specification/2025-06-18),
built on [LibTmux](https://www.nuget.org/packages/LibTmux).

<!-- libtmux-logo -->
</div>
<!-- /libtmux-logo -->

> **Releases.** Releases are numbered `0.1.N`, and each release increments `N`.
> The API is not settled: any release may change or remove exported identifiers,
> and the changelog marks each break. Pin an exact version to avoid one.

## Quick start

Install the .NET tool, then register it with Claude Code. The client starts the
server itself and speaks to it over standard input and output:

```console
$ dotnet tool install --global LibTmux.Mcp
```

```console
$ claude mcp add tmux -- libtmux-mcp
```

`claude mcp add` confirms the registration, and the next client session lists
the server's tools.

## Point a client at it

[libtmux.org](https://libtmux.org/en/csharp/latest/mcp/#install) has the exact
snippet for Claude Code, Claude Desktop, Codex, Cursor, Gemini and other
clients. A client that reads a JSON configuration takes the same command:

```json
{
  "mcpServers": {
    "tmux": {
      "command": "libtmux-mcp"
    }
  }
}
```

With the .NET 10 SDK the client can run it straight from NuGet, with no
install step:

```json
{
  "mcpServers": {
    "tmux": {
      "command": "dnx",
      "args": ["LibTmux.Mcp", "--yes"]
    }
  }
}
```

To pin a version, write it after an `@`, as in `LibTmux.Mcp@<version>`, using
a version from [NuGet](https://www.nuget.org/packages/LibTmux.Mcp).

- A client started from a desktop launcher does not inherit your shell.
- If the .NET SDK came from a version manager, set `DOTNET_ROOT` in the server's
  `env` so the tool can find its runtime. The
  [native config swapper](https://github.com/libtmux/libtmux-dotnet/blob/master/eng/mcp-swap/README.md)
  does it for you.

The server drives its own dedicated socket by default. To drive a named server,
pin its socket in the environment:

```json
{
  "mcpServers": {
    "tmux": {
      "command": "libtmux-mcp",
      "env": {
        "LIBTMUX_SOCKET": "my-socket"
      }
    }
  }
}
```

Claude Code takes the same variable with `-e`:

```console
$ claude mcp add tmux \
    -e LIBTMUX_SOCKET=my-socket \
    -- libtmux-mcp
```

Earlier releases accepted `"args": ["my-socket"]`. Remove that positional
argument and put the socket name in `LIBTMUX_SOCKET`; the executable now reads
its target only from the startup environment.

## What it is for

Anything where the answer is on a terminal screen: run a build and learn whether
it passed, watch a dev server come up, find which of eleven panes is showing the
stack trace, lay out a workspace and drive it.

- [`run_shell_command`](https://libtmux.org/en/csharp/latest/mcp/tools/run_shell_command/)
  runs a command and returns the shell's real exit status.
- [`wait_for_text`](https://libtmux.org/en/csharp/latest/mcp/tools/wait_for_text/)
  waits for output you did not start.
- [`capture_pane`](https://libtmux.org/en/csharp/latest/mcp/tools/capture_pane/)
  reads visible text and scrollback.
  [`snapshot_pane`](https://libtmux.org/en/csharp/latest/mcp/tools/snapshot_pane/),
  [`search_panes`](https://libtmux.org/en/csharp/latest/mcp/tools/search_panes/),
  and
  [`capture_since`](https://libtmux.org/en/csharp/latest/mcp/tools/capture_since/)
  give structured and incremental reads.
- No tool returns unbounded output, and a failure says what failed.
- Pane modes, such as copy mode and menus, belong to people. The server never
  enters, drives, or exits one, and input tools refuse a pane that is in one.
  Wait for the person to leave.

## Configuration

| Variable | Default | Does |
|---|---|---|
| `LIBTMUX_SOCKET` | `libtmux-mcp` | One socket name pinned at startup |
| `LIBTMUX_SOCKET_PATH` | *(unset)* | One absolute socket path, mutually exclusive with `LIBTMUX_SOCKET` |
| `LIBTMUX_TMUX_CONFIG` | bundled minimal configuration | An explicit absolute tmux configuration path |
| `LIBTMUX_TOOLSETS` | provenance-dependent | Unordered `inspect`, `manage`, `execute`, and `teardown` selection |
| `LIBTMUX_TOOLS` | *(unset)* | Additional exact tool names |
| `LIBTMUX_EXCLUDE_TOOLS` | *(unset)* | Exact tool names removed after inclusion |
| `LIBTMUX_TMUX` | `tmux` | Which tmux binary to drive |
| `LIBTMUX_MCP_WAIT_MAX_SECONDS` | `30` | Ceiling on any one wait |
| `LIBTMUX_MCP_MAX_LINES` | `500` | Default line budget |
| `LIBTMUX_MCP_MAX_BYTES` | `128000` | Byte budget per result |
| `LIBTMUX_MCP_ALLOW_POLLING_FALLBACK` | `false` | Permit pane text waits to poll after control observation fails (tmux 3.7 and newer; older releases always poll) |

### Waiting

- On tmux 3.7 and newer a text wait uses tmux's control mode. If it cannot
  start or the stream is lost, the wait ends. Below 3.7 no control client is
  attached, so waits poll without the setting below.
- Set `LIBTMUX_MCP_ALLOW_POLLING_FALLBACK=true` only when repeated pane reads
  are acceptable.
  [`wait_for_text`](https://libtmux.org/en/csharp/latest/mcp/tools/wait_for_text/)
  then re-reads the pane every 60 ms, the result says `pollingFallback: true`,
  and a warning goes to stderr.
- [`run_shell_command`](https://libtmux.org/en/csharp/latest/mcp/tools/run_shell_command/)
  does not use this setting. If it times out or is cancelled, the command may
  still be running.

### Choosing tools

- A newly created dedicated socket gets all four toolsets. An existing or
  user-configured socket omits `teardown` unless you select it.
- Exclusions always win over inclusions.
- Startup stops on an unknown toolset or tool name, an empty item in a list,
  both socket variables at once, an empty or relative `LIBTMUX_TMUX_CONFIG`, and
  `LIBTMUX_SAFETY` in the environment.
- Toolsets and filters shape what the client sees and can call. Execute tools
  run with the tmux user's authority over files, processes, and the network.
- [`tmux://capabilities`][api-mcp-capabilities] reports the pinned socket, the
  tool selection, and every effective tool. Each tool also carries its row under
  `_meta["com.git-pull.libtmux-mcp/capability"]`.
- On shutdown the server removes only a dedicated daemon it launched. It leaves
  existing or replaced daemons running.

To offer a client only the tools that read tmux, select the `inspect` toolset:

```console
$ claude mcp add tmux \
    -e LIBTMUX_TOOLSETS=inspect \
    -- libtmux-mcp
```

To keep the other tools and remove
[`send_keys`](https://libtmux.org/en/csharp/latest/mcp/tools/send_keys/) and
[`send_keys_batch`](https://libtmux.org/en/csharp/latest/mcp/tools/send_keys_batch/),
exclude them by name:

```console
$ claude mcp add tmux \
    -e LIBTMUX_EXCLUDE_TOOLS=send_keys,send_keys_batch \
    -- libtmux-mcp
```

### Typing into panes

- [`send_keys`](https://libtmux.org/en/csharp/latest/mcp/tools/send_keys/),
  [`send_keys_batch`](https://libtmux.org/en/csharp/latest/mcp/tools/send_keys_batch/),
  and
  [`run_shell_command`](https://libtmux.org/en/csharp/latest/mcp/tools/run_shell_command/)
  refuse a pane that is in a mode.
  [`paste_text`](https://libtmux.org/en/csharp/latest/mcp/tools/paste_text/)
  checks only the pane it names.
- With `synchronize-panes` on, input to one pane reaches every pane in that
  window whose setting is on.
  [`set_synchronize_panes`](https://libtmux.org/en/csharp/latest/mcp/tools/set_synchronize_panes/)
  is the only tool that turns it on.
- [`run_shell_command`](https://libtmux.org/en/csharp/latest/mcp/tools/run_shell_command/)
  refuses when synchronized panes would run the command in more than one, so its
  status and output stay singular.
- Checks before sending are observations. A pane can change mode after the
  check, and the pane IDs in a result say who was configured to receive input,
  not who received it.
- [`call_read_tools_batch`](https://libtmux.org/en/csharp/latest/mcp/tools/call_read_tools_batch/)
  takes up to 16 `operations`, each a `tool` and its `arguments`.
  [`send_keys_batch`](https://libtmux.org/en/csharp/latest/mcp/tools/send_keys_batch/)
  takes the same, and both take `onError: "stop"` or `"continue"`.

## Which pane am I in?

- When the client that launched this server was itself inside tmux, the server
  knows its own pane from `TMUX_PANE` and says so in its instructions.
- Every pane listing marks that pane `isCaller`, so an assistant can avoid
  typing into the terminal it is talking through.

## Confirm a build without a client

```console
$ { printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}'; sleep 3; } | libtmux-mcp
```

- The pause keeps standard input open, as a real client does. Closing it
  immediately tears the session down while the reply is still being written, and
  you get no bytes back.
- The pause has to outlast the server's start, which includes starting its tmux
  server, so allow a few seconds.

List the tools a selection offers, again without a client. This sends the
handshake and then `tools/list`, and prints each tool's name:

```console
$ { printf '%s\n' \
    '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}' \
    '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
    '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'; \
    sleep 3; } \
  | LIBTMUX_TOOLSETS=inspect libtmux-mcp \
  | jq -r 'select(.id == 2) | .result.tools[].name'
```

## What it leaves out

- **Host commands.** `tmux://capabilities` reports zero host-command tools.
- **Detached jobs.**
  [`run_shell_command`](https://libtmux.org/en/csharp/latest/mcp/tools/run_shell_command/)
  is synchronous and bounded, and there are no detached job handles.
- **Dynamic resources.** `tmux://capabilities` is the only resource, with no
  templates or subscriptions.
- **Pane modes.** The server never enters, drives, or exits one.
- **Authorization.** Toolsets and filters change what a client can see and call.
  The server runs with the tmux user's authority.

## Support and status

- **Releases.** Releases are numbered `0.1.N`, and each release increments `N`.
  The API is not settled: any release may change or remove exported identifiers,
  and the changelog marks each break. Pin an exact version to avoid one.
- **tmux.** Whatever `tmux` resolves to on the path, or the binary
  `LIBTMUX_TMUX` names. The supported range is 3.3a to 3.8, proven from source
  on every commit.
- **The floor.** `tmux://capabilities` reports it as
  `connection.minimumTmuxVersion`. A tmux below it stops the server at startup.
- **An older daemon.** A daemon replaced by an older one fails the tool call.
  The message says to upgrade tmux and restart the tmux server, or to use
  LibTmux.Mcp 0.0.0-alpha.21, and that nothing was sent.
- **.NET.** The tool targets .NET 8 and .NET 10.
- **Systems.** Linux, including WSL, and macOS. CI also builds on Windows x64,
  where the tool exits with "tmux does not run on Windows."
